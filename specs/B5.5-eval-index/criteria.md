# B5.5 acceptance criteria

**IDX-01** Index page on the EvalKit site: per project, headline metric with CI, calibration stamp, gate status, EvalKit version and run date, from `summary.json` at a pinned commit; no model calls [D-61]
Refined: `evalkit index build` (and `evalkit.index.build_index`) reads only local files — the registry, `configs/index.yaml` and the snapshot folder written by the separate `evalkit index snapshot` step, which records the commit every file was read at — and writes `index.html` and `index.json`, byte-reproducible. Per project (seven registered, EvalKit eighth): the configured headline row with its 95% interval and method (exactly one row, else the problem; not designated when no selector), the calibration stamp (EvalKit: judge kappa per judge or uncalibrated; metrics-1: the configured row or not stated), the gate status through `evalkit.gates.evaluate` (EvalKit default gates for a summary without a gates file; not gated for metrics-1 without one), the EvalKit version (recorded, or not recorded with the registry pin), the run date, run id, commit and `simulated` (D-63). `index.json` carries the portfolio's `story` keys (`headline`, `evals`, `improvements`, `learnings`, `monitoring`) in the shapes of inputs.md. No model, network or clock is used in the build.

**IDX-02** A project whose summary cannot be read is shown as missing, never dropped or guessed [D-61]
Refined: every registered project and EvalKit appear, in registry order. No summary registered, no snapshot, a bad snapshot.json, a failed fetch, an absent file, a file changed since the snapshot (sha256), bad UTF-8 or JSON, another project's own `summary.json` format (the strict run-folder reason), an invalid metrics-1 or RunSummary, or any unexpected error gives `missing` with that reason and no figure from anywhere else; a broken gates, run.json or experiments file shows its own reason without hiding the summary; nothing crashes the page; `--require-all` exits 1 when any project is missing.

**EFF-04** Per project and model, the efficiency block on the index next to quality, with cost per correct as the comparison metric [D-67]
Refined: per value of the `model` label, the configured quality row beside the standard efficiency names (EFFICIENCY_NAMES: cost per correct and per case, tokens in/out/reasoning/cached, cache-hit share, latency p50/p95/p99, error and retry rate, system cost, eval overhead, mode, price date) with intervals where given; a pre-0.3 EvalKit summary falls back to its point cost and latency figures, labelled no interval; several rows for one name and model show `ambiguous`, never one of them; models are ordered by cost per correct (unknown last), the lowest marked, `clear` only when its interval lies below every other model's, else `intervals overlap`; a project without model labels says so.

Safety for all three: held-out rows only at split level (split, model, judge); no case or member ids, no secrets (key shapes hidden), every value escaped and limited to 64 characters; lesson and answer text never copied; `.env` and paths outside the repository refused by the snapshot step.
